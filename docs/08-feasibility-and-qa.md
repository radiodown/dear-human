# 08. 가능성 검증과 QA

[문서 목록](../README.md) · **현재 모든 실행 검증 항목은 미실행이다.** 아래는 검증 계획과 기록 양식이다.

## 1. 판정 원칙

웹 코드 작성 가능성, 파츠형 캐릭터와 무기 재사용, 생성 참고물·적 프레임의 품질, 반동·머리·바스트의 보조 모션, 혈액·진액, 브라우저 실행 성능을 각각 확인한다. 특히 `그럴듯한 GIF`와 `엔진에서 조작하며 쓸 수 있는 모션`을 구분한다. 실제 캐릭터·총구 효과를 연결한 작은 실험부터 시작한다.

임시 도형으로 진행 규칙을 시험하는 것은 허용한다. 다만 생성 도구의 가능성 통과 근거로 사용하지 않는다. 수치 기준은 이번 프로토타입의 제안 목표이며 실측 결과가 아니다.

## 3. 모션·총구 측정 방법

캐릭터의 발 원점, 이미지의 총구 끝, 엔진 소켓 점을 서로 다른 색으로 표시한다. 정지·이동·좌우 반전을 각각 기록한다. 가능하면 모든 프레임의 오버레이 이미지를 저장한다.

- 총구 오차: `화염 시작점과 이미지 총구 끝의 거리`, 논리 화면에서 2px 이하.
- 발 기준선: 의도한 발 들기와 몸통 흔들림을 구분한다. 공통 원점의 불필요한 상하 이동은 1px 이하.
- 크기 변화: 머리·몸통의 예상하지 않은 크기 변화 2px 이하 목표. 원근 없는 측면이라는 기준에서 본다.
- 외형 고정: 보조 변형을 끈 기본 프레임에서 검은 긴 머리·첨부 비례·전술 갑옷·망토·3D 재질을 확인한다. 의도한 보조 모션과 생성 오류를 구분한다.
- 군집생물 외형: 갑각·낫 모양 발톱·다리·꼬리의 개수와 연결을 확인한다. 꼬리 잘림·발톱 증식·사람형 보행으로의 변형이 없어야 한다. 낮은 몸통에도 수평 사격이 정상적으로 명중해야 한다.
- 상태 전환: 대기↔이동, 정지 사격↔이동 사격, 좌↔우를 20회 반복하고 순간적인 무기 소실·크기 튐이 없어야 한다.
- 원본 검수: 투명도·캔버스·프레임 수 등 구조 검사와 손·총 일관성 시각 검사를 모두 기록한다.

모든 모션에 정확히 2px라는 자동 점수를 낼 수 있다는 의미가 아니다. 총구 좌표처럼 측정 가능한 항목과 육안 판정을 구분해 기록한다.

## 5. 사격과 효과의 일대일 검수

shot_id마다 발사 시각, 총구 월드 좌표, 방향, 충돌 대상, 피해, 생성된 효과 ID를 연결한다. 100회 발사에서 총구 화염 트리거는 100회여야 한다. 실제 적 명중에만 적용된 피해가 기록돼야 한다.

100발 등의 모션/효과 검수는 실제 장전을 거쳐 유효 발사 수를 누적한다. 순수 연사율을 따로 측정할 때만 G-04의 진단 탄창 설정을 사용하고 기본 30발 설정과 구분해 기록한다. 빈 총·장전 중 입력은 shot_id·반동·화염·발사 수를 늘리지 않는다.

damage_id마다 final_damage·hp_loss·스침/일반/약점·is_critical·재질·숫자·분사 ID를 기록한다. explosion_id는 대상별 피해와 연결하고 사망 원인·선택 프로필도 남긴다. 플레이어의 무적 거부는 분사 0회여야 하고, 벽 명중에는 진액이 없어야 한다. 분사를 hit_confirmed와 damage_applied 양쪽에서 중복 생성하지 않는다.

효과가 상한 때문에 회수되는 스트레스 상황은 별도로 표시한다. 화염 수를 맞추려고 같은 발사에 여러 번 피해를 적용하는 구조가 되어서는 안 된다.

## 6. 성능 측정

목표는 기준 데스크톱의 웹 브라우저에서 60 FPS다. 현재 기준 PC와 실측값은 미정이다. CPU·GPU·RAM·OS·브라우저/버전·Phaser/런타임 버전·WebGL 정보·DPR·캔버스 크기·빌드·녹화 여부를 기록한다. Chrome·Edge 우선, Firefox 추가 검증으로 시작한다.

| 시나리오 | 측정 구간 | 제안 기준 |
|---|---|---|
| 일반 플레이 | 10초 워밍업 후 60초 | 프레임 시간 p95 ≤16.7ms, p99 ≤33.3ms |
| 적 20마리·최대 연사·모핑·피격 효과 | 스트레스 배치 후 60초 | 같은 프레임 기준, 액적 128·잔흔 48 등 상한 유지 |
| 반복 재시작 | 5회 재시작 | 월드 개체·효과 잔류 없음, 메모리 지속 증가 없음 |

스트레스 장면은 디버그로 적 20마리를 명시적으로 배치해 확보한다. 기본 웨이브는 생성 간격 때문에 최대 상한까지 쌓이지 않을 수 있다. 측정 전에 리소스를 한 번 로드해 최초 임포트·셰이더 준비와 정상 실행 비용을 구분한다.

개발 서버와 Vite production build를 구분하고, 빌드의 로컬 preview에서도 확인한다. 평균 FPS만으로 통과시키지 않는다. DevTools Performance 기록으로 JS·렌더링·GC를 구분하고, 녹화가 영향을 주면 성능 로그와 품질 영상을 분리한다. 최초 다운로드 바이트·로드 시간과 정상 실행 구간도 별도로 기록한다.

## 7. 제작 비용 검증

최초 파츠 원화·리깅·공통 동작, 무기 1개 자산·소켓·파지 보정, 갑옷 부위의 자산·관절·가림·fit 보정, 생성 참고물·적 프레임의 비용을 분리한다. 생성 작업은 행동당 3회 수정 루프를 제안 시작 예산으로 두고 리깅·IK 작업량은 별도 측정한다. 시간을 줄이기 위해 심각한 손·무기 불일치를 통과시키지 않는다.

통과하더라도 모션 하나마다 장시간 수작업이 필요하면 전체 캐릭터·스킬 확장에 필요한 비용을 다시 추정한다. 이번에는 플레이어 1명만으로 검증하므로 여러 캐릭터로 확장되는 생산성을 이미 입증했다고 보지 않는다.

## 9. 최종 판정 규칙

- **진행:** F-01~F-05·M-01~M-15·L-01~L-06·C-01~C-10·S-01~S-09·R-01~R-10·필수 기능을 통과하고 기준 브라우저 성능을 만족한다. 실제 제작 비용을 수용할 수 있다.
- **조건부 진행:** 플레이는 가능하지만 제한된 수정 작업이나 명확한 성능 조정이 남아 있다. 남은 항목·예상 작업량·재검증 조건을 적는다.
- **보류:** 이동 사격의 동일성·총구 정렬을 예산 안에 확보하지 못하거나, 기본 전투·성능 문제가 해소되지 않았다. 실패 근거와 비교할 대안을 적는다.

모션이나 효과를 다른 제작 방식으로 대체하면 게임 프로토타입의 진행 여부와 원래 도구 조합의 채택 여부를 각각 기록한다.

현재는 군집생물 1종의 생성·전투만 검증한다. 데이터가 종류 ID를 갖는다는 사실만으로 미래의 원거리·비행·대형 적이 동작한다고 판정하지 않는다. 해당 종류를 실제로 추가할 때 별도 검증한다.
