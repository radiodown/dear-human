# 21. 스토리 진행·컷신·대화·스킵

[문서 목록](../README.md) · 요구사항을 반영한 설계이며 스토리 런타임·연출 에셋은 아직 구현하지 않았다.

## 1. 플레이에서의 역할

게임은 횡스크롤 전투 사이에 **컷신과 미연시식 대화**로 인물 관계와 사건을 진행한다. 모든 스토리 연출에는 즉시 사용할 수 있는 스킵을 제공한다. 세계관·인물·첫 임무의 기준은 [15](15-worldbuilding.md)이며 이 문서는 전달 방식과 실행 규칙을 정한다.

서사적 플레이어인 인간 지휘관과 전투에서 조작하는 배속 클론을 구분한다. 지휘관은 전진 지휘소에서 현지 통신으로 대화하고, 조작 클론은 기존 분홍 일자 중단발·제복·M16 외형을 유지한다. 스토리 기능 때문에 별도의 조작 캐릭터를 추가하지 않는다.

## 2. 초기 구현 범위

| 요소 | 이번 1스테이지 | 후속 확장 |
|---|---|---|
| 도입 | 임무 설명 대화와 짧은 카메라·포즈 연출 1묶음 | 장면 추가·인물별 에피소드 |
| 종료 | 출구 도달 후 임무 보고 대화 1묶음 | 다음 임무·관계 서사 연결 |
| 대화 화면 | 화자명·본문·입력 안내·다음·스킵 | 선택지·백로그·자동 넘김·음성 |
| 인물 표시 | 기존 캐릭터 파츠·리그 재사용, 화자 강조 | 필요한 표정·상반신 전용 이미지·Live2D 별도 검토 |
| 컷신 | 기존 배경·리그의 위치·포즈·카메라 큐 | 영상·장편 시네마틱·전용 컷 이미지 |
| 분기 | 선형 진행, 선택지와 호감도 없음 | 선택·분기·결과 조건을 데이터로 확장 |
| 설정 | 이번 실행의 스토리 표시 켜기/끄기 | 저장 기반 읽은 내용만 빠르게 넘기기 |

기본안은 도입 4~6문장, 종료 2~4문장과 각각 2~5초 이내의 짧은 실시간 연출이다. 본문은 사용자 속도로 넘기며 시간 제한을 두지 않는다. 초기 목표인 전투 2~4분과 별도로 스토리 관람 시간을 기록한다. 대규모 대본·신규 인물 원화·영상 제작은 모션 검증보다 먼저 확대하지 않는다.

도입에서는 도로 확보 목적과 지휘관/클론의 임무 관계를, 종료에서는 대피·보급 통로 확보 결과를 보여준다. 미정인 생물의 기원·음모·결말을 대사로 확정하지 않는다. 장면 ID 기본안은 `stage_01_intro`, `stage_01_outro`다.

## 3. 넘기기와 스킵

| 조작·설정 | 동작 |
|---|---|
| `Enter` / `Space` / 본문 영역 클릭 | 출력 중이면 현재 문장 전체 표시, 이미 다 표시됐다면 다음 문장 |
| 화면의 `스토리 스킵` / `K` | 현재 대화·컷신 묶음 전체를 즉시 완료하고 다음 플레이 상태로 전환 |
| `Esc` | 일시정지 메뉴. 스토리 스킵과 복귀 제공 |
| 시작 화면의 `스토리 표시: 끄기` | 새 실행에서 도입·종료의 연출을 생략하고 동일한 완료 처리 |

다음 문장과 장면 전체 스킵은 다른 버튼으로 구분한다. 스킵에 확인창·긴 누르기·최소 관람 시간은 요구하지 않는다. 전환·타이핑·카메라 이동 중에도 스킵 버튼을 유지한다. 키보드 포커스로 버튼을 실행할 수 있고 입력 안내를 표시한다.

키 반복과 연속 클릭이 여러 상태를 통과하지 않도록 한 번의 누름에 한 행동만 처리한다. 스토리 입력은 전투 입력보다 우선하며, 종료 때 눌린 키·마우스와 고정 틱 누적 시간을 비운다. 넘기기 클릭이 총알을 발사하거나 종료 입력이 결과 화면의 재시작까지 실행해서는 안 된다. 전투는 새로 누른 입력부터 받는다.

초기 설정은 메모리 안의 이번 실행에만 보관한다. 스테이지 재시작은 새 run_id를 만들며 설정에 따라 다시 관람하거나 스킵한다. 읽은 내용만 자동으로 넘기는 기능과 브라우저 재접속 후 읽음 기록 복원은 저장 기능을 도입할 때 추가한다. **스킵 완료와 실제 읽음은 별도 기록**이며, 생략한 문장을 읽었다고 표시하지 않는다. 미래의 선택지 노드는 자동 스킵을 멈추고 선택을 기다린다. 스킵이 임의로 선택지나 호감도 결과를 정하지 않는다.

## 4. 게임 상태와 시간

```text
READY → STORY(stage_01_intro) → PLAYING → STORY(stage_01_outro) → CLEAR
                                  └──→ FAILED
PLAYING / STORY ↔ PAUSED(복귀할 상태 보관)
CLEAR / FAILED → 새 run_id의 READY
```

도입 동안 이동·사격·AI·스폰·접촉 피해·플레이 타이머는 시작하지 않는다. 전투 중간에 필수 정지 대화를 추가한다면 같은 STORY 상태로 들어가며 전투 스냅샷을 보존한다. 초기판은 구역마다 전투를 끊는 대화를 추가하지 않는다.

출구에서 생존·3구역 완료를 검사하고 결과를 한 번 고정한 뒤 종료 스토리를 연다. 같은 틱 HP 0은 기존처럼 실패가 우선한다. 종료 관람/스킵에 따라 HP·처치·발사 수·전투 시간·클리어 결과가 달라지지 않는다. 종료 연출이 끝나기 전에는 재시작 입력을 받지 않는다.

STORY에서는 전투 시계와 별도의 연출 시계만 흐른다. 카메라·대사 타이핑·연출 포즈는 연출 시계를 쓴다. 탭 숨김·포커스 상실은 연출도 정지하고 복귀 후 재개를 기다린다. 밀린 대사·연출·발사를 몰아서 처리하지 않는다.

## 5. 권장 구현

기존 Phaser·TypeScript 앱에 작은 데이터 기반 `StoryRunner`와 `DialogueOverlay`를 추가한다. 별도 게임 엔진이나 대화 전용 사이트를 만들지 않는다. `CutscenePlayer`는 기존 CharacterView/RigAdapter·배경·카메라를 사용하고 UI는 기존 UIScene에서 표시한다. 이 구성은 프로젝트 설계안이며 외부 도구의 자동 변환 기능을 전제하지 않는다.

| 모듈 | 책임 |
|---|---|
| StoryRegistry | 장면 ID·텍스트·등장인물·참조·완료 결과를 사전 검증 |
| StoryRunner | 노드·타이핑·다음·스킵·정상 완료·취소 관리 |
| DialogueOverlay | 화자·본문·스킵·포커스·입력 안내 |
| CutscenePlayer | 카메라·포즈·표시/퇴장 큐와 취소 가능한 작업 묶음 |
| SessionController | 상태 전환·진행 플래그·장면 완료의 단일 반영 |
| InputRouter | 스토리/전투/메뉴 입력 문맥·이벤트 소비·눌림 초기화 |

대사와 연출 큐는 표현만 담당한다. 진행 플래그·다음 상태는 장면의 `completion`에 모아 선언한다. 개별 애니메이션 콜백이나 대사 마지막 글자에 적 스폰·클리어·보상을 숨기지 않는다. 관람 완료와 스킵은 같은 `completeScene(run_id, scene_id, reason)` 경로를 사용한다.

완료 처리는 활성 run_id·장면을 확인하고, `(run_id, scene_id)` 완료 키 기준으로 한 번만 반영한다. 플래그 설정과 다음 상태 전환을 한 작업으로 적용한다. 중복 클릭·연출의 늦은 콜백·이전 실행 콜백은 무시한다. 스킵은 남은 큐를 순서대로 빠르게 실행하지 않고 즉시 취소 후 완료 결과를 반영한다. 신규 실행은 새 키를 쓰므로 도입 처리가 누락되지 않는다.

타이머·Tween·텍스트 출력·연출 음성·카메라 제어는 장면 소유의 취소 묶음으로 관리한다. 스킵/종료 때 정리하고 전투 카메라·저장된 행동의 포즈·입력 문맥을 복원한다. [22](22-weapon-reloading.md)의 장전 중 진입했다면 탄수·경과 시간·손/탄창 위상도 보존하며 스킵으로 보충하지 않는다. 이 과정에서 실제 전투 피해·스폰 이벤트를 발행하지 않는다. 향후 영상 사용 시에도 재생 실패·중단과 무관하게 같은 스킵 경로를 유지한다.

## 6. 데이터 계약 예시

아래는 향후 `game/src/data/story/stage_01_intro.json`에 둘 자체 형식의 설계 예시다. 아직 해당 파일·런타임이 존재한다는 뜻은 아니다. 본문은 임시 대본이다.

```json
{
  "schema_version": 1,
  "scene_id": "stage_01_intro",
  "stage_id": "stage_01",
  "phase": "intro",
  "nodes": [
    {
      "node_id": "establish",
      "type": "cutscene",
      "cue_id": "checkpoint_establish",
      "duration_sec": 2
    },
    {
      "node_id": "briefing",
      "type": "dialogue",
      "speaker_id": "commander",
      "text": "수송도로를 확보한다. 대피 차량이 통과할 길을 열어 줘."
    },
    {
      "node_id": "response",
      "type": "dialogue",
      "speaker_id": "clone_01",
      "text": "확인했습니다. 검문소로 진입합니다."
    }
  ],
  "completion": {
    "set_flags": { "stage_01_briefed": true },
    "next_state": "PLAYING"
  }
}
```

종료 장면은 같은 구조로 `phase: outro`, `stage_01_debriefed: true`, `next_state: CLEAR`를 사용한다. `briefed/debriefed`는 관람 여부와 무관한 스토리 진행 플래그다. 실제 읽음 기록은 표시가 완료된 노드만 별도로 수집한다. 초기 장면은 순차 배열이며, 분기용 임의 스크립트 실행이나 eval을 넣지 않는다.

장면/노드 ID 중복, 알 수 없는 화자·큐·다음 상태, 음수/무한 재생 시간, 단계와 맞지 않는 완료 전환을 로드 때 검사한다. 완료 대상은 장면을 열기 전에 확정한다. 읽을 수 없는 그림·음성이면 텍스트·스킵으로 진행하고, 필수 데이터가 잘못됐다면 재시도/시작 화면 복귀와 오류를 제공한다. 검증하지 못한 완료 경로로 전투 상태를 추측해 변경하지 않는다.

## 7. 통합 샘플과 반복 작업

기존 [18. 통합 샘플](18-preview-library-and-reuse.md)에 `#/samples/stories/stage_01_intro`와 종료 장면 페이지를 추가한다. 대사와 카메라 큐를 모션마다 다른 사이트로 나누지 않는다. 동일 StoryRunner로 전체 재생·노드 재생·중간 스킵·빠른 중복 입력·탭 복귀를 확인하고, 관람 완료와 스킵의 상태·플래그·통계를 비교한다.

샘플은 격리된 세션을 사용하므로 본편 진행·읽음 기록을 변경하지 않는다. 스토리는 별도 StoryRegistry에 등록하고 현행 시각 에셋 목록의 kind를 임의로 추가하지 않는다. 연결된 캐릭터·무기·배경·표정 자산은 실제 존재하는 버전만 참조한다.

대사 수정은 텍스트와 관련 장면 검수만 갱신하고 캐릭터·무기·걷기·사격을 재생성하지 않는다. 큐 수정은 해당 장면, 공통 StoryRunner 수정은 모든 스토리 샘플을 재검수한다. 장면별 텍스트/큐 revision과 에셋 의존 버전을 기록한다. 현행 자동화 CLI는 Markdown 링크·JSON 구문만 검사하며 장면 계약 검사·스킵 실행 검증은 후속 구현이다.

## 8. 완료 조건

도입/종료를 관람하거나 어느 지점에서 스킵해도 같은 다음 상태·전투 결과에 도달해야 한다. 누락/중복 스폰·총알·클리어·콜백·카메라 잔류가 없어야 한다. [08](08-feasibility-and-qa.md)의 S 검수를 수행하고 기존 통합 샘플에 증거를 남긴다. 현재는 설계만 반영했으며 실행 검증은 모두 미실행이다.
